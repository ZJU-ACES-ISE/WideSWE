Show node hierarchy/nesting details in Phoenix trace view for complex workflows.

When sending workflow traces from Dify to Phoenix (Arize), the trace view currently displays all spans as a flat list. Dify workflows often contain nested structures - loops, conditional branches, parallel executions, and sub-workflow nodes - that have parent-child execution relationships. Phoenix should not lose which nodes belong to which loop iteration, which nodes are inside a conditional branch, or the nesting depth of sub-workflows.

Improve Phoenix trace hierarchy for workflow, chatflow, nested workflow, and workflow-as-tool execution. Establish stable workflow root/session semantics for top-level and nested workflows, reconstruct node hierarchy from execution metadata, graph parents, structured parents, and safe root fallbacks, and propagate private workflow-as-tool parent trace context without overwriting user workflow inputs. Bridge nested workflow spans back to the outer workflow tool span. If parent context is temporarily unavailable, retry trace dispatch without duplicate enterprise trace emission.

`ToolNode.run()` should restore or create the current node execution id before obtaining the tool runtime, and the tool runtime protocol should receive that id as `node_execution_id`. Preserve legacy tool node parameter handling: historical tool nodes with `version == "1"` and no `tool_node_version` should continue to pass `variable_pool=None` to the runtime, current tool nodes should continue to pass the real `VariablePool`, and runtime adapters should use the explicit `node_execution_id` protocol.
